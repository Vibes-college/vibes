# 上线前检查（Vibes College）

2026-11-16 起，社区代码每次上局域网测试站、上正式站之前，都要先过一遍上线前检查。不过关就不上。
由质量把关定，创始人 2026-11-16 10:47 PT 同意补工程规范。

## 查什么

| 项 | 做什么 | 不过的常见原因 |
|---|---|---|
| 代码规矩 | `node scripts/check-shipping.mjs --base <上游版本标签>`：改过的文件跑 eslint，查版权文件头（SPDX）、语言文件 | 格式不对；新文件没写版权文件头（检查会自动补上，补了也算不过，要先提交补好的文件） |
| 我们的测试 | 后端 `packages/backend/test/unit/Lojo*.ts`、前端 `packages/frontend/test/unit/lojo/*`，还要核对条数 | 有测试没过；测试被跳过；条数比下限少（测试被删了，或题目、计划表没找到） |
| 数据库改动 | 在一个一次性的空 Postgres 18 + Redis 上，从头跑完全部迁移，再跑 `check-migrations` | 改了 entity 没写迁移，或者删了迁移 |

- **条数下限**：2026-11-16 时后端是 244 条，前端是 211 条，写在 `preflight.sh` 开头的 `MIN_BACKEND` 和 `MIN_FRONTEND` 里。
  - 加了测试，就把下限调高。
  - 删测试要写清楚为什么，再调低。
  - 为什么要数条数：题目和计划表不在这个仓库里。找不到它们的时候，有 24 条测试不会报错，而是直接消失，结果照样显示「全过」。
- **数据库改动这一项有盲区**：我们自己的 `lojo_*` 表是手写 SQL，没有 entity，这一项看不见它们（2026-11-16 试过，删掉 LojoPlan 迁移照样通过）。对这些表，它只能证明迁移在空库上能从头跑通。改 `lojo_*` 表时，要靠测试和测试站人工核对。
- **不跑后端「全部单元测试」**：其中一部分会清空它连到的数据库。2026-11-12 就因为这个，把测试站的数据清掉过一次。

## 怎么跑

脚本不在这个仓库里，在私有工作区的 `apps/community/scripts/preflight.sh`。

```sh
apps/community/scripts/preflight.sh                       # 检查 source/
apps/community/scripts/preflight.sh --src source/.wt-xxx  # 检查某个工作树
apps/community/scripts/preflight.sh --no-cache            # 不用上次「通过」的记号，强制重跑
```

- 在编译容器里跑：脚本会自己找到把这份代码挂在 `/workspace` 的那个容器。
- 代码要先编译过（`pnpm build`）。
- `build-runtime.sh` 会在编译完、换测试站之前自动跑。
- `deploy.sh` 会在上正式站之前自动跑（`--dry-run` 也会跑，但只报告结果，不拦）。
- `--rollback`、`--restart`、`--prune` 都不跑：出事时退回上一版，不能被检查耽误。

## 要多久

2026-11-16 在 Mac 上实测，总共 30 到 35 秒：

| 项 | 用时 |
|---|---|
| 代码规矩 | 约 22 秒（最慢，因为要对上游改过的约 400 个文件跑 eslint） |
| 后端测试 | 约 3 秒 |
| 前端测试 | 约 3 秒 |
| 数据库改动 | 约 5 秒 |

同一个提交，代码干净、已经通过过，12 小时内再跑会直接算过。比如 `build-runtime.sh` 刚跑过，紧接着 `deploy.sh` 就不用再等一遍。

## 安全

- 迁移检查用的临时库在一个单独的、不通外网的 docker 网络里，跑完就删。
- 跑之前，会照代码自己读配置的方式先读一遍。读到的数据库不是那个临时库，就停下不跑。
  - 2026.10.x 及更早的版本读的是编译好的 `.config.json`，它指向测试站的库，所以在这些版本上这一项会报「没跑」。
- 跑完会清理干净：临时库、Redis、临时网络、`.config/preflight-*.yml`、复制进容器的题目，被打断也一样清理。

## 没过怎么办

1. 看屏幕上那张 PASS / FAIL 表，再看 `/tmp/vibes-preflight/<时间>/` 里对应的日志。
2. 修好、提交，再跑一遍。
3. 要是这个不过以前就有，而不是这次改动引起的：也先修，或者找质量把关一起定。不要把下限调低来糊过去。
4. 真的十万火急、必须先上（比如正式站正在出事，修复已经在测试站确认过）：
   ```sh
   deploy.sh --approved-by "..." --skip-preflight "<为什么、谁同意的>"
   build-runtime.sh --skip-preflight "<为什么、谁同意的>"
   ```
   - 原因不能空。
   - 原因和时间会记进本机 `~/.vibes/preflight.log`，正式站的上线记录里也会写 `preflight=skipped:<原因>`。
   - 事后要补跑一遍。
